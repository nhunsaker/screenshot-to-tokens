# Text contrast: the fourth verify check

Verify now runs four checks before a PR opens. The first three are pixel diffs (fallbacks identical, color merges
invisible, all tokens for review). The fourth measures **text contrast against WCAG 2.x AA, success criterion 1.4.3**:
4.5:1 for body text, 3:1 for large text (24 px and up, or 18.66 px and up at weight 700 and above).

What this is: one named check, on the captured route, with a number. What it is not: an accessibility audit. Don't
describe a run as "accessible" or "compliant". Do say what was measured, for example "41 text pairs fell below the
WCAG AA contrast minimum on Argon; the proposal adds none".

## What is checked

Every element that owns visible text on the captured page (its own text nodes, including inside open shadow roots),
in three renders that verify already takes:

| Render | Screenshot | Text samples from |
|---|---|---|
| Original | `screenshot.png` (capture) | the noise-baseline load of the unchanged page |
| Color tokens only | `after-colors.png` | the same load |
| All tokens | `after.png` | the same load |

Not counted, with a reason in `verify.json.contrast.skipped`:

- `disabled`: inside a disabled control or group (`:disabled`, `fieldset:disabled`, `aria-disabled="true"`), or the
  label of one. SC 1.4.3 exempts inactive UI components.
- `decorative`: text with no letters or digits (separators, `•••`, `→`). The ACT rule exempts text that expresses
  nothing in a human language.
- `invisible`: text the same color as what is under it (1:1), which the ACT rule treats as not presented text.
- `offscreen`: positioned outside the page (`top: -999em`).
- `no-glyphs`: the DOM says the text is a color, but nothing of that color is painted where the text is. Usually the
  text is covered by an overlay (a cookie banner, a fixed header). It is not visible in this render, so it is not
  scored. Hidden text (`display: none`, `visibility: hidden`, opacity 0) never becomes a sample.

## Method

Text color comes from the DOM: the computed color (or `-webkit-text-fill-color` when it differs), times the opacity of
the element and all its ancestors. The **background is measured on the rendered pixels** under the text
(`src/stages/text-contrast.js`, `sampleBackground`):

1. Take the pixels inside the element's own text runs (Range client rects, one per line fragment), not its whole box.
   A label at the left of a long gradient is measured where its letters are.
2. Find the ink: pixels within ΔE 6 (CIE76) of the text color, plus anti-aliased blends lying on the line from the
   text color to the main background at 40% coverage or more. Translucent text is composited over each main background
   color first, since it paints a different ink on each.
3. Drop the ink and a 1 px band around it (the anti-aliasing), then keep the ring 2 to 4 px from the letters: the
   background they are read against. A text-shadow halo or a gradient under the words shows up there.
4. Cluster the ring's colors (ΔE 5). Clusters covering at least 5% of the ring count, so a stray icon pixel or a
   neighbour's border cannot decide the verdict.
5. The pair's ratio is the **worst** counted cluster (the gate's conservative reading). The best one is kept as well,
   because the W3C ACT rule scores the highest possible contrast.

The gate: pairs are matched across renders by path, text and occurrence. **A proposal must not add a failing pair**: a
pair that met its minimum on the original page and falls below it in either after-render fails verify. Failures the
page already had are reported, not blocking. `verify.json.contrast` holds `pairs`, `failingBefore`, `failingAfter`
(per render), `regressions`, `improved`, and `failing` (each with ratio, minimum, large-text flag, box, measured colors
and the token(s) whose value is the text color, text-color tokens first). The report has a fourth verify row with the
counts and a table of failing pairs; the PR body has a "Text contrast (WCAG 2.x AA)" section grouped by color pair,
each row naming the token to change.

Color merges move values by up to ΔE 3, which can push a pair across 4.5:1 in either direction. On acme-shop the two
"New" badges go from 4.45:1 to 4.51:1 because `#1b74e9` merges into `#1a73e8`; a merge the other way would be a
regression and would fail verify, even though the pixel check calls it invisible.

## Results

The three existing checks are unchanged: fallback-only 0 px, colors 0.000%, all tokens 0.919%. Text contrast:
**87 pairs measured, 41 below the AA minimum on the original page, 41 after the proposal, 0 regressions.**

L11's DOM audit in the playground also found 41. A static DOM resolve from `capture.json` (nearest containing

header gradient (2.05:1 against `#11c5ef`) and "Jessica Jones" on the other end of a gradient (4.0:1 against `#1177ef`).

### Benchmark A: W3C ACT rule afw4f7 (text has minimum contrast)

`node scripts/bench-act-contrast.mjs` fetches the official test cases
(`https://www.w3.org/WAI/content-assets/wcag-act-rules/testcases.json`), loads each page in Playwright the way verify
does, and scores the page outcome (failed if any text fails, passed if any was checked and all pass, inapplicable if
nothing was checked).

The file lists 34 cases for afw4f7: **32 approved (11 passed, 10 failed, 11 inapplicable)** and 2 proposed (not yet
approved: "Passed Example 7" with an `aria-label`ed button, "Failed Example 11" with a text-shadow that lowers
contrast). The spec's "11/11/11" counted one proposed case.

| Reading | Approved cases consistent | Exact outcome |
|---|---|---|
| ACT (highest-contrast cluster) | **32/32** | 31/32 |
| Gate (worst cluster) | 32/32 | 31/32 |

By expected outcome: passed 11/11 consistent (10 exact), failed 10/10, inapplicable 11/11. ACT counts an implementation
consistent when it fails every failed example and fails none of the others. The one inexact case is Passed Example 7
(`----=====+++…`): we report it inapplicable (decorative, no letters) where the rule says passed. Neither reading fails it.

Cases worth naming, because they are where a DOM-only checker has to give up or guess:

- Passed 2 / Failed 2 (gradient): measured under the words, 12.23:1 best and 5.12:1 worst for `#333` (pass); 2.11:1
  best for `#AAA` (fail).
- Passed 3 / Failed 3 (text on a photo): 12.59:1 best for `#ccc` with a shadow; 2.71:1 best for `#555` (fail).
- Passed 4 (black on `#737373` with a white text-shadow): 5.53:1 against the halo; the plain background is 4.42:1.
- Failed 4 / Failed 5 (alpha text, `opacity: .3`): composited, 2.11:1.
- Failed 7 (translucent text over a half-transparent, half-black background): 4.23:1 best, 2.3:1 worst.
- Inapplicable 6 to 11 (disabled controls and their labels): skipped as `disabled`.

The proposed cases split the two readings: Failed 11 (shadow lowers contrast) is fail in the gate reading (3.52:1) and
pass in the highest-contrast reading (5.0:1); Passed 7 (`X` with `aria-label="Close"`, 3.66:1) fails in both, since we
don't treat a single letter as non-language text. Gate reading on all 34: 33 consistent.

## Limits

- **Not a full audit.** This is one success criterion. Not covered: keyboard access, focus order and visibility,
  screen-reader semantics (names, roles, landmarks), hover, focus and active states, placeholders and input values,
  motion, and **non-text contrast** of icons and controls (SC 1.4.11; that is L16, with SAM regions).
- One route, one viewport (1440x900), the state the page loads in. Text revealed by interaction is not measured.
- Text covered by an overlay is not scored (`no-glyphs`); if the overlay is dismissible, the text under it still
  needs checking.
- Text drawn into images or canvas is not text to the DOM and is not measured (the ACT rule treats it the same way).
- The ink detector assumes the text is painted in its computed color. Gradient-filled text (`background-clip: text`)
  and heavy text effects read as `no-glyphs` or as whatever the ring shows.
- The worst-cluster reading is stricter than ACT's highest-possible-contrast reading by design: text half on a light
  and half on a dark background fails the gate if either half is below the minimum.
- Ratios are rounded to two decimals and compared with the exact minimum (4.5 or 3); 4.49:1 fails.
